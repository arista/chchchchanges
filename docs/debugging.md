# Debugging and Logging

The library provides a mechanism for logging operations, which can be useful when debugging complex chains of dependencies.  It logs the following events:

* transaction start
* transaction end
* ChangeSource before notification
* ChangeSource after notification
* detectChanges enter
* detectChanges exit
* add dependency

## id generation

Some notifications contain id's that can tie them together.  These id's are simply generated using an incrementing counter.

## Named ChangeSources

ChangeSources are assigned names, as are detectChanges calls.  These names can be provided by the application (passed in to enableChanges or detectChanges), or they can be generated by the system.

ChangeSource names are based on a "base object name", which is what the application would pass in to enableChanges.  If no base name is provided then the system will assign a name of the form {object type}#{generated id}.  The {object type} is "Object", "Array", "Map", "Set", etc.

The ChangeSource name is then derived from the base object name according to these rules:

### Object ChangeSources

* prototypeOf - {base name}.<prototype>
* isExtensible - {base name}.<extensible>
* ownPropertyDescriptor - {base name}.propertyDescriptor({property name})
* hasProperty - {base name}.has({property name})
* property - {base name}.{property name}
* ownKeys - {base name}.<keys>

### Array ChangeSources

An Array has only one ChangeSource, whose name is the same as the Array's base name.

### Map ChangeSources

* key - {base name}.{key}
* hasKey - {base name}.has({key})
* size - {base name}.<size>
* keys - {base name}.<keys>
* clear - {base name}.<clear>

### Set ChangeSources

* has - {base name}.has({key})
* size - {base name}.<size>
* keys - {base name}.<keys>
* clear - {base name}.<clear>

### CachedFunction ChangeSources

A CachedFunction has only one ChangeSource, whose name is the same as the CachedFunction's base name.

## Chained names

It's expected that an application will directly call enableChanges only a few times, maybe even only once to establish a root object.  Other calls to enableChanges are implied when objects are automatically wrapped as arguments or return values to already-enabled objects.  For those cases, it's useful if names could be assigned to those objects that would be meaninful to the application.

For example, if an enabled object is called "Profile", and another object is set on that first object using Profile.address = Address, it would be nice if that Address object were automatically assigned a meaningful base name like "Profile.address".

To do this, we apply these rules to the implicit enableChanges call performed at various stages:

* Object.set(property, value) - the value is assigned a base name of "{Object's base name}.{property}".  Note, special rules (below) are applied if the Object is an Array
* Object.get(property) -> value - the value is assigned a base name of "{Object's base name}.{property}".  Note, special rules (Below) are applied if the Object is an Array
* Map.set(key, value) - the value is assigned a base name of "{Map's base name}.{key}"
* Map.get(key) -> value - the value is assigned a base name of "{Map's base name}.{key}"

* Array.set(property, value) - the value is assigned a base name of "{Array's base name}[{property}]"
* Array.get(property, value) - the value is assigned a base name of "{Array's base name}[{property}]"

Note that for the above cases, once a base name is assigned, it remains as it was set, even if that value is moved to a different object, removed from the object, etc.  The exception is array element values.  For those items, the base name should be updated every time Object.set/get is called.

## Named Listeners

Each invocation of detectChanges() is called a "ChangeDetection", and is assigned a name based on a generated id.  If detectChanges is called with a name, then the ChangeDetection is named {name}#{generated id}.  If no name is provided, then the listener is named "DetectChanges#{generated id}".

## Named Domains

Domains can optionally be created with names.  Otherwise they are assigned name "Domain#{generated id}"

## Events

The following Events are generated for logging and debugging:

```
ChangeEvent = one of the following

{
  type: "TransactionStarted"
  domain: {domain name}
  transaction: {transaction id}
}

{
  type: "TransactionEnded"
  domain: {domain name}
  transaction: {transaction id}
}

{
  type: "BeforeChangeNotified"
  domain: {domain name}
  transaction: {transaction id}
  source: {change source name}
  detectChanges: {ChangeDetection name}
}

{
  type: "AfterChangeNotified"
  domain: {domain name}
  transaction: {generated transaction id}
  source: {change source name}
  detectChanges: {ChangeDetection name}
}

{
  type: "DetectChangesEntered"
  domain: {domain name}
  detectChanges: {ChangeDetection name}
}

{
  type: "DetectChangesExited"
  domain: {domain name}
  detectChanges: {ChangeDetection name}
}

// Indicates that a detectChanges call was interrupted by nested detectChanges call
{
  type: "DetectChangesSuspended"
  domain: {domain name}
  detectChanges: {ChangeDetection name}
}

// Indicates that a detectChanges call resumed after a nested detectChanges call exited
{
  type: "DetectChangesResumed"
  domain: {domain name}
  detectChanges: {ChangeDetection name}
}

// Indicates that a detectChanges call identified a dependency on a ChangeSource
{
  type: "ChangeSourceReferenced"
  domain: {domain name}
  source: {change source name}
  detectChanges: {ChangeDetection name}
}

```

## API

The logging mechanism is configured when an application calls "create" on a Changes to obtain a ChangeDomain, where it has the opportunity to pass in a logging function.

If no logging function is passed in, then the library should do as much as it reasonably can to avoid having any debugging mechanisms impede the performance of the library.
